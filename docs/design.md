# LeadSight — Data Model & Adapter Contracts

Version 0.3 · September 2026

Changes from 0.2: API contract defined with oRPC in `packages/contract` (contract-first,
shared by api and web, TanStack Query integration); Biome for lint/format; per-area
conventions in `.claude/skills/`.

Changes from 0.1: scoring split into evidence extraction (LLM) + versioned rules
(deterministic); separate confidence score; `criteria` replaces `output_schema`
on campaigns; `evidence`, `confidence`, `rules_version` on leads.

## 1. Overview

A campaign-driven social listening engine. Sources produce raw posts, an
extractor pulls structured evidence from each post against a campaign, a rule
set turns evidence into a score, and matches land in a lead inbox. Nothing
offer-specific lives in code; all of it is campaign data.

```
Sources (Reddit API, Alerts RSS)
   │
   ▼
 posts ──▶ Extractor (LLM: Groq → Gemini) ──▶ evidence ──▶ Rules (versioned, deterministic) ──▶ leads ──▶ Inbox / Alerts
                 ▲                                                                                   │
                 └──────────── labels (won / lost / not_fit) as few-shot examples ◀─────────────────┘
```

Design principle borrowed from evidence-based qualification tools: the model
finds facts, fixed rules assign points. Same evidence always yields the same
score; the inbox shows the score line by line; thin evidence is reported as
"insufficient" rather than a confident guess.

Stack: Fastify service (API, auth, scheduler, adapters, scoring) · oRPC contract
shared by api and web · Next.js dashboard with TanStack Query/Table · Postgres via
Drizzle · Better Auth with `organization` plugin · Biome.

## 2. Data model (Postgres)

All business tables carry `organization_id` from day one. Better Auth manages
`user`, `session`, `account`, `organization`, `member`, `invitation`.

#### 2.1.1 criteria

An ordered list, generated by the setup chat from the user's description of the
campaign and stored on the campaign row. Nothing in the pipeline knows what any
key means; the extractor answers the questions, the rules engine sums the
points. Each criterion tells the extractor what to look for and tells the rules
engine how many points it is worth. Weights sum to 100.

Criteria are generated once per campaign, not per scoring call, so that scores
are reproducible, the breakdown has stable axes, and weights can be tuned with
instant rescoring. Editing criteria (manually or via the chat) bumps
`rules_version`.

Example for a "founders seeking an MVP team" campaign (a "JavaScript contract
jobs" campaign would get an entirely different list from the same flow):

```json
[
  {
    "key": "explicit_ask",
    "question": "Is the author explicitly asking for a CTO, technical co-founder, developer, agency or team to build something?",
    "type": "boolean",
    "weight": 30
  },
  {
    "key": "stage",
    "question": "What stage is the product at?",
    "type": "enum",
    "options": ["idea", "prototype", "live"],
    "points": { "idea": 20, "prototype": 15, "live": 5 },
    "weight": 20
  },
  {
    "key": "budget_signal",
    "question": "Does the author mention funding, budget, or willingness to pay?",
    "type": "boolean",
    "weight": 25
  },
  {
    "key": "engagement_model",
    "question": "Do they want an equity-only co-founder, a paid partner, or unclear?",
    "type": "enum",
    "options": ["equity_only", "paid", "unclear"],
    "points": { "equity_only": 0, "paid": 15, "unclear": 7 },
    "weight": 15
  },
  {
    "key": "author_is_nontechnical",
    "question": "Does the author present as non-technical (business/domain background)?",
    "type": "boolean",
    "weight": 10
  }
]
```

Types: `boolean` (full weight if true), `enum` (points per option, capped at
weight), `number` (linear scale between `min`/`max`, capped at weight).

Re-scoring: when `campaign.criteria` changes, existing leads keep their
version. A "re-score campaign" action re-runs rules only (no LLM call) over
stored evidence, so it is free and instant; a full re-extract is a separate,
explicit action.

#### 2.5.1 evidence

```json
{
  "criteria": {
    "explicit_ask":   { "value": true,   "quote": "looking for a CTO to build the first version", "confidence": 95 },
    "stage":          { "value": "idea", "quote": "haven't built anything yet",                   "confidence": 85 },
    "budget_signal":  { "value": null,   "quote": null,                                           "confidence": 30 },
    "engagement_model": { "value": "unclear", "quote": null,                                      "confidence": 40 },
    "author_is_nontechnical": { "value": true, "quote": "I come from hospitality",                "confidence": 80 }
  },
  "disqualifier_hits": [],
  "summary": "Hospitality founder with an idea for a booking SaaS, looking for a CTO, no budget mentioned."
}
```

Every criterion carries the quote it was derived from. `null` value means "not
found", and contributes 0 points.

## 3. Adapter contracts (TypeScript)

Plain modules. No Fastify dependency, so they run from tests and one-off scripts.

### 3.1 Source

```ts
export interface RawPost {
  platform: Platform;
  externalId: string;
  url: string;
  authorHandle?: string;
  authorUrl?: string;
  title?: string;
  body: string;
  bodyIsSnippet: boolean;
  postedAt?: Date;
  raw: unknown;
}

export interface SourceRunResult {
  posts: RawPost[];
  nextCursor: unknown;      // opaque, persisted to sources.cursor
  warnings?: string[];
  usage?: { searchQueries: number };   // metered calls; the pipeline books them
}

export interface Source<C = unknown> {
  readonly kind: SourceKind;
  validateConfig(config: unknown): C;                 // throws on bad config
  run(config: C, cursor: unknown): Promise<SourceRunResult>;
  /** Optional: fetch the full body when the source only had a snippet. */
  hydrate?(post: RawPost): Promise<RawPost>;
}
```

Rules:

- Adapters receive `fetch`, credentials and a clock at construction (through
  `createSourceRegistry(deps)`), never from globals, so `run` keeps this exact
  shape and tests inject a fake fetch. `SourceRunResult.warnings` is always
  present (possibly empty).
- `run` is read-only and idempotent for a given cursor. Re-running with the
  same cursor must not duplicate posts; dedupe happens on
  `(platform, external_id)` at insert time regardless.
- Cursors are per source so a missed run catches up on the next one.
- Hydration is per **platform**, not per source, and lives on the registry
  (`registry.hydrate(post)`): LinkedIn public post GET (crawler UA), X oEmbed,
  Reddit public post page GET (crawler UA, reads the server-rendered
  `<shreddit-post>`; never listings, never the API), nothing for Facebook or
  generic web (snippet only). Blocked or changed markup keeps the snippet.
- Any source failure sets `sources.last_error`; it never stops other sources.
- Kinds whose credentials are missing are registered as *disabled* adapters:
  config still validates, `run` fails with a clear non-retryable error, so
  the source shows why in `last_error` instead of vanishing.

**Source strategy (2026-09-09).** The Reddit Data API now requires manual
approval (Responsible Builder Policy), approvals are rare, and the
unauthenticated `.json`/RSS endpoints return 403; see `docs/reddit-access.md`.
Discovery on Reddit, LinkedIn and X therefore goes through Google search over
each platform's public pages, polled actively; Google Alerts RSS stays as the
free secondary net. reddit.com is never scraped for discovery.

Implementations in v1:

- `GoogleSearchSource` (`google_search`, **primary**) — Google Programmable
  Search JSON API (`GOOGLE_CSE_KEY`, `GOOGLE_CSE_CX`). One query per source
  per poll: `site:<scope> ("p1" OR "p2" …)`, max 10 phrases, `dateRestrict`
  = lookback (`d1`), `sort=date`, 10 results; page 2 only when page 1 was
  full. Results are filtered to post pages per platform (`/comments/`,
  `/posts/`, `/status/`…), become snippet posts (`external_id` = canonical
  URL) and are hydrated later. Cursor `{ lastQueryAt, query }` is
  informational; dedupe at insert makes repeats harmless. Each run reports
  `usage.searchQueries` (1–2), which the pipeline books against the daily
  query budget (§4).
- `RssSource` — parses any RSS/Atom feed (Google Alerts), cursor
  `{ newestPublished }`; `platform` taken from config; `external_id` is the
  canonical target URL.
- `RedditSubredditSource` / `RedditSearchSource` (**optional**, disabled
  without API credentials) — Reddit OAuth, `/r/{sub}/new` with cursor
  `{ newest: fullname }`, and `/search` with `sort=new`, cursor
  `{ newestCreatedUtc }`.

### 3.2 Extractor (LLM)

```ts
export interface ExtractionInput {
  campaign: CampaignForPrompt;   // offer, icp, disqualifiers, criteria
  examples: LabeledExample[];    // from labels, capped at campaign.fewshot_limit
  posts: RawPost[];              // batched, typically 5–10
}

export interface ExtractionOutput {
  postExternalId: string;
  evidence: Evidence;            // shape from 2.5.1
}

export interface Extractor {
  extract(input: ExtractionInput): Promise<{
    results: ExtractionOutput[];
    provider: string;
    promptVersion: string;
  }>;
}
```

`LlmExtractor` implements this with an OpenAI-compatible client, a provider
chain `[groq, gemini]`, retry once on 429/5xx (honouring `Retry-After`), strict
JSON output validated with Zod before anything is written. Unknown or malformed
results for a post are re-asked once, alone, then returned in `dropped` with a
reason; the pipeline writes the `extract.dropped` event. The model never sees
weights or thresholds; it only answers the criterion questions with a value, a
quote and a per-field confidence.

`extract` additionally returns `dropped`, token `usage`, and `provider` as
`<name>/<model>` (stored on the lead). The model is asked for a JSON *object*
`{ "results": [...] }` because JSON mode requires an object root. Token budget
is per provider per UTC day, summed across organizations (caps are per API key),
persisted as `llm.usage` rows in `events`; a provider at ≥ 90% of its cap is
skipped, and when none is left the extractor throws `BudgetExhaustedError` so
posts stay unscored for the next run.

### 3.3 Rules (deterministic)

```ts
export interface RulesResult {
  score: number;                       // 0–100
  breakdown: Record<string, number>;   // points per criterion key
  confidence: number;                  // 0–100
  verdict: 'hot' | 'warm' | 'cold' | 'insufficient' | 'disqualified';
}

export function applyRules(campaign: Campaign, evidence: Evidence): RulesResult;
```

Pure function, no I/O, unit-tested against fixtures. Algorithm:

1. If `evidence.disqualifier_hits` is non-empty → `disqualified`, score 0.
2. For each criterion, points = f(value) per type in 2.1.1; `null` → 0.
3. `score` = sum of points.
4. `confidence` = weighted mean of per-field confidences, weighted by criterion
   weight, reduced by 20 if `post.body_is_snippet`.
5. If `confidence < campaign.min_confidence` → `insufficient`.
6. Else `hot` / `warm` / `cold` by `campaign.thresholds`.

Because this is pure, the inbox can show "what if" re-scoring when weights are
edited before the campaign is saved.

### 3.4 Notifier

```ts
export interface Notifier {
  notify(leads: LeadSummary[], campaign: Campaign): Promise<void>;
}
```

Called with all new leads at or above `min_score_alert` (and not
`insufficient`/`disqualified`) after each scoring run, batched per campaign.

v1 ships **`EmailDigestNotifier`** only (decided 2026-09-09; a chat notifier
such as Slack is deferred until there is a need — it would be one more
implementation of this interface plus an optional field in `notifications`).
The digest sends at most one email per campaign per 24 h to
`campaigns.notifications.digestRecipients`; when due, it covers every
alertable lead scored since the previous digest (so leads that arrived while
the notifier was waiting are not lost), capped at 50, ranked like the inbox.
Each send is a `notify.email_digest` event, which is also how the interval is
enforced across restarts; a failed send writes no event and is retried on the
next run. Transport is `Mailer` (`packages/core/src/notify/mailer.ts`),
implemented in the API with nodemailer (`SMTP_URL`, `SMTP_FROM`) or a
log-only fallback.

## 4. Pipeline

Runs inside the Fastify process on a scheduler (node-cron; swap to BullMQ if
retries/visibility become painful).

1. **Poll** — for each enabled source that is due: `run`, upsert posts, write
   `post_sources`, persist cursor. Due = `poll_interval_min` elapsed, or
   `active_hours.offInterval` elapsed when the source is outside its active
   hours (evaluated in the source's time zone; `pipeline/schedule.ts`).
   `google_search` sources additionally back off to 2 h while the search
   query budget is ≥ 90% spent (resets at midnight UTC).
2. **Pre-filter** — cheap local check: post must contain at least one campaign
   keyword or the source must be `reddit_search`/`rss` (already keyword-scoped).
   Everything else is kept as a post but not extracted. Implemented inside the
   candidate query, so filtered posts never occupy the batch window.
3. **Hydrate** — posts with `body_is_snippet = true` and a hydrator available.
4. **Extract** — for each campaign, batch unscored candidate posts, load
   few-shot examples, call the extractor, store evidence.
5. **Score** — `applyRules` per lead, store score, breakdown, confidence,
   verdict, `rules_version`.
6. **Notify** — leads above threshold.
7. **Log** — one `pipeline.run` event per organization touched, carrying
   counts, errors and the per-source breakdown the dashboard shows; plus
   `source.run`, `source.error`, `extract.dropped`, `extract.error` and
   `extract.budget_exhausted` events as they happen.

Budget guards (per UTC day, per API key, so usage is summed across
organizations; both live in `extractor/budget.ts` and are stored as events):

- LLM tokens per provider (`llm.usage` events). A provider at ≥ 90% of its
  cap is skipped for the day and the next provider is used — logged, never
  silent. When every provider is over its cap, extraction stops for the run
  and the posts remain candidates for the next day.
- Google search queries (`search.usage` events, `GOOGLE_CSE_DAILY_QUERIES`,
  default 100 = the free tier). At ≥ 90% the search source skips its run
  with a warning and the scheduler stretches `google_search` intervals to
  2 h until midnight UTC; a request that got an HTTP answer counts even when
  it failed.

## 5. Campaign setup chat

Endpoint `POST /campaigns/draft` takes the conversation so far plus optional
URLs. It fetches the URLs, then makes one LLM call with a strict schema and
returns a draft:

```json
{
  "name": "...",
  "offer_description": "...",
  "icp": "...",
  "disqualifiers": ["..."],
  "keywords": ["..."],
  "criteria": [ /* shape from 2.1.1, with suggested weights */ ],
  "thresholds": { "hot": 70, "warm": 40 },
  "suggested_sources": [
    { "kind": "reddit_subreddit", "config": { "subreddit": "startups" } },
    { "kind": "reddit_search", "config": { "query": "..." } }
  ],
  "alert_queries": ["site:linkedin.com/posts \"...\""]
}
```

The UI shows the draft as an editable form, with criteria weights as sliders
that must sum to 100. Saving creates the campaign at `rules_version = 1` and
its sources. `alert_queries` are shown as copy-to-clipboard strings; the user
creates the Google Alerts manually and pastes the feed URLs back as `rss`
sources.

Implementation notes: the wire shape is camelCase (`campaignDraftSchema`, owned
by core and re-exported by the contract); the example above shows the fields.
The endpoint returns `{ reply, draft }` where `draft` is `null` when the model
still needs one answer from the user (the `reply` is then the question). Model
output is normalised before validation (key casing, weights rescaled to 100,
enum points capped) and re-asked once with the validation issues; the same
provider chain and token budget as extraction apply. Admin role required.

## 6. Extraction prompt (template)

System: you are extracting evidence from public posts to judge fit with an
offer. Answer each criterion strictly from the post text. Quote the supporting
text. If a criterion is not addressed, return `null` with low confidence. Do
not guess. Return only JSON.

User content, assembled per call:

- Offer: `{offer_description}`
- Ideal poster: `{icp}`
- Disqualifiers: `{disqualifiers}` — report any that apply
- Criteria: list of `{key, question, type, options}` (no weights)
- Examples: up to N labeled posts with `positive`/`negative` and the reviewer note
- Posts: array of `{id, title, body, platform}`

Output: array of `{id, evidence}` with the shape in 2.5.1. `prompt_version` is
bumped whenever this template changes and stored on every lead.

## 7. API surface (v1)

Defined as an oRPC contract in `packages/contract/src/index.ts`; that file is
authoritative. Summary of routes (each procedure also carries a REST `method`/`path`
so an OpenAPI handler can be added later without changing the contract):

```
POST   /auth/*                      Better Auth
GET    /campaigns                   list
POST   /campaigns/draft             setup chat → draft
POST   /campaigns                   create (with sources)
PATCH  /campaigns/:id               edits to criteria bump rules_version
POST   /campaigns/:id/rescore       re-run rules over stored evidence (no LLM)
GET    /campaigns/:id/sources
POST   /campaigns/:id/sources
PATCH  /sources/:id                 enable/disable, config
POST   /sources/:id/run             manual run
PATCH  /campaigns/:id/rescore/preview  verdict movement for edited weights, no save
GET    /leads?campaignId=&verdict=&status=&platform=&assigneeId=&minScore=&sort=&cursor=
PATCH  /leads                       bulk status/assignee
PATCH  /leads/:id                   status, assignee
POST   /leads/:id/notes
GET    /runs                        recent pipeline runs with per-source counts
GET    /runs/budget                 tokens used today per provider
```

Transport: oRPC `RPCHandler` on `/rpc/*` for the web app (typed client, TanStack Query
utils). Better Auth on `/api/auth/*`. Plain Fastify `GET /healthz`.

All routes scoped by the active organization from the session, and gated by the
member's role in it: `member` reads and triages leads; `admin` additionally
manages campaigns and sources, runs sources and rescores; `owner` additionally
deletes and changes organization settings.

## 8. Open decisions

- ORM: **Drizzle** (decided). Schema in TS, `drizzle-kit generate` for
  migrations committed to git, applied as a deploy step — `pnpm db:migrate`
  (drizzle-kit) in development, `node dist/migrate.js` (drizzle-orm's migrator
  over the same folder, no drizzle-kit in the image) as the compose `migrate`
  service in production — never at service boot, so a bad migration cannot
  take the API down mid-rollout; `push` only for local iteration. Better Auth
  tables emitted via its CLI into the same schema.
- Hosting: **one machine, Docker Compose** (`deploy/compose.yml`): Postgres,
  migrate, api, web, Caddy. One public origin; Caddy routes `/api/*`, `/rpc/*`,
  `/healthz` to the API, the rest to Next.js. Same-site cookies, no CORS in
  production. Split hosts (api.\<domain\>) would need `crossSubDomainCookies`.
- Session cookie cache: enabled for the web app, but the API always reads the
  session from the database when building the request context. The active
  organization is the tenant boundary and must never be served stale.
- Test isolation: one Postgres database per test, cloned from a template with
  the committed migrations applied (`CREATE DATABASE … TEMPLATE`). Schema-per-
  test was rejected because generated migrations qualify enum types with
  `public`. See the `postgres-drizzle` skill.
- Labels: the newest label for a (campaign, post) is the one that counts. A
  later won/lost/not_fit decision replaces the earlier label rather than adding
  a second row, so few-shot examples never contradict each other.
- Scheduler: node-cron in-process for v1; move to BullMQ when a second worker
  is needed.
- Keyword pre-filter on RSS: skip entirely (feeds are already keyword-scoped)
  or apply a looser check. Start with skip.
- Confidence penalty for snippet-only posts: fixed −20 or per-platform. Start
  fixed.
